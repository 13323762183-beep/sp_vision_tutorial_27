# Lecture4 Homework：QoS Debugger

## 任务一：实现 Publisher 和 Subscriber 的通信

### 1. 实验现象

首先运行原始代码，启动发布者和订阅者，发现订阅者无法正常接收到消息。

### 2. 查看话题的 QoS 配置


```bash
ros2 topic info /sensor_data --verbose
```

这条命令查看话题的发布者和订阅者数量，以及各自的 QoS 配置，包括 Reliability、History 和 Depth 等信息。

结合输出并追查源代码，发现发布者默认使用 `best_effort`尽力而为，订阅者默认使用 `reliable`可靠通信。两者的可靠性策略不兼容，导致订阅者无法与发布者建立有效的通信匹配。

### 3. 修改代码

修改 `src/qos_debugger/src/qos_debugger_pub.cpp` 中的默认参数：

```cpp
this->declare_parameter("reliability", "reliable");
```

将发布者的默认可靠性策略修改为 `reliable`，使其与订阅者兼容。

修改后重新编译并运行，订阅者能够正常接收消息，任务一完成。

## 任务二：分析并解决消息丢包问题

### 1. 查看节点参数

使用以下命令查看发布者和订阅者的运行参数：

```bash
ros2 param get /sensor_publisher rate
```

该命令用于查看发布者的发布频率，原始默认值为 100 Hz。


```bash
ros2 param get /sensor_subscriber depth
```

该命令用于查看订阅者的队列深度，原始默认值为 10。


```bash
ros2 param get /sensor_subscriber callback_delay_ms
```

用于查看订阅者的回调延迟，原始默认值为 30 ms。

回调延迟是指订阅者收到一条消息后，在回调函数中额外等待一段时间，再继续处理消息。即代码中的callback_delay_ms 参数，这里每处理一条消息就额外等待 30 ms，订阅者一秒最多处理33.3条消息。但发布者以 100 Hz 发送消息，即每秒约 100 条。因此，消息到达速度超过处理速度，队列积压。当队列深度为 10 且持续积压时，较旧的待处理消息可能被丢弃，表现为序列号不连续、出现丢包警告。



### 2. 丢包原因

修改 QoS 后，订阅者能够正常接收消息，但运行过程中出现序列号不连续的警告，而累计丢包数量始终为 0。

结合参数和源代码分析，发布者每秒发布约 100 条消息，而订阅者每处理一条消息需要额外等待 30 ms，理论处理能力约为 33 条/秒。订阅者处理速度低于发布速度，队列积压后可能发生消息丢失。

同时，检查 `qos_debugger_sub.cpp`，发现代码检测到序列号缺失后只打印警告，没有更新累计丢包数量。

### 3. 修复丢包统计

在 `topic_callback()` 中，找到检测到序列号缺失的代码，增加：

```cpp
lost_count_ += lost;
```
使后续计算的累计丢包率能够反映检测到的序列号缺口。

修改后，警告信息仍然存在，但累计丢包数量和丢包率能够正确反映检测到的消息缺口。

### 4. 调整回调延迟并验证

将订阅者的默认回调延迟从 30 ms 修改为 0：

```cpp
this->declare_parameter("callback_delay_ms", 0);
```

重新编译并运行后，订阅者接收的序列号变得连续，累计丢包数量为 0，丢包率为 0.00%。

实验说明，回调延迟会影响订阅者的处理能力。减少人为延迟后，订阅者能够跟上发布者的发送速度，丢包现象得到改善。

## 任务三：计算并打印接收帧率

### 1. 帧率计算公式

接收帧率（FPS）表示单位时间内订阅者实际接收到的消息数量：

\[
FPS=\frac{\Delta N}{\Delta t}
=\frac{N_{\mathrm{current}}-N_{\mathrm{last}}}
{t_{\mathrm{current}}-t_{\mathrm{last}}}
\]

其中，\(\Delta N\) 为两次统计之间新增的接收消息数量，\(\Delta t\) 为两次统计之间实际经过的时间。

### 2. 代码实现思路

在 `qos_debugger_sub.cpp` 的 `report()` 定时器回调函数中，获取当前时间，计算新增的接收消息数量和实际经过时间，再计算并打印 FPS。

统计完成后，更新上一次的接收数量和统计时间，作为下一次计算的基准。

### 3. 实验结果与理解

运行程序后，订阅者每隔约一秒输出一次接收帧率。实验中接收帧率稳定在约 99–100 FPS，与发布者设置的 100 Hz 基本一致。

通过本次实验，我理解到发布频率不等于实际接收帧率。接收帧率需要根据订阅者实际收到的消息数量和经过时间计算。使用实际时间间隔进行计算，也可以减少定时器执行时间波动带来的影响。
